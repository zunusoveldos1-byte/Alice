# Потоковая озвучка и время жизни QBuffer

Дата: 20 октября 2026 года.

## Реализованный поток

LLMProvider.stream → SentenceChunker → asyncio.Queue(maxsize=2) →
SAPI/Edge-TTS → queued Qt PCM signal → FIFO контроллера → QAudioSink.

Ollama получает stream=true; Gemini использует SSE streamGenerateContent.
Совместимый generate() собирает ответ из нового итератора. Служебные
thought-части Gemini не попадают в текст. Сохраняются лимиты символов,
токенов, заголовок ключа и безопасные сообщения об ошибках.

Producer и consumer работают в TaskGroup; очередь ограничена. Перед
синтезом нужен кредит. Одновременно возможно не более трёх PCM,
включая воспроизводимый; суммарные байты проверяются в runtime и GUI
по MAX_PCM_BYTES (32 MiB). Возврат кредита требует совпадения token и
sequence; повторные и старые подтверждения игнорируются.

Каждый credit возвращается после сигнала завершения воспроизведения.
Runtime ждёт окончания producer/consumer и подтверждений всех PCM,
затем обновляет историю и посылает dialog_done. Controller завершает
сеанс после этого маркера и опустошения локального выхода. Ошибка или
отмена очищает очередь и не добавляет частичный ответ в историю.

Qt-аудиоресурсы создаются и изменяются в GUI-потоке. Workers передают
неизменяемый PCM через queued signals. GUI не ждёт сеть, TTS или потоки.
Обновления текста GUI ограничены 20/с с обязательным финальным обновлением.

## Исправление QBuffer

open(ReadOnly) уже присутствовал в исходном коде. Регрессионный тест
воспроизвёл закрытие QBuffer обработчиком IdleState прямо внутри start().
Теперь результат open проверяется, завершение отложено через QTimer,
а обработчики привязаны к конкретному sink. Отложенные и поздние события
старого sink не закрывают буфер следующего фрагмента.

## Проверки

- Полный unittest-набор: 83 теста, OK (4.559 с на финальном запуске).
- 18 новых streaming-тестов проверяют ранний HTTP delta/PCM, Gemini header
  и thought filtering, закрытие ответа, пунктуацию, числа, сокращения,
  разбитую между дельтами Markdown-ссылку, EOF без пунктуации, лимит текста,
  FIFO, паузу, stale tokens/credits, отмену, лимит PCM и обновление истории.
- Проверена пауза длиннее timeout_s с заполненными очередями и успешное
  продолжение. Сетевой stall при этом всё ещё завершается ProviderError.
  Таймаут считает только активное ожидание iterator/HTTP, а не время yield.
- Проверены отказ QBuffer.open, reentrant IdleState и поздний сигнал
  предыдущего QAudioSink.
- GUI --smoke: код 0. pip check: No broken requirements found.
- Ревью выявило таймаут через yield и разрыв Markdown-ссылок; оба дефекта
  воспроизведены тестами и исправлены. Повторное ревью замечаний не выявило.

Автономные asyncio-тесты выполнялись разрешённым запуском вне песочницы;
они не используют микрофон, настоящие ключи и сетевые сервисы.

## Нативная проверка

scripts/tts_check.py с настоящими SAPI Irina и Qt, громкость 0:
три воспроизведения завершились, позиция буфера при паузе сохранилась,
COM-поток завершился; код 0. Среднее TTS 179.9 мс, p50 83.6 мс;
среднее PCM → выход 913.0 мс, p50 99.7 мс. Первая холодная проба
PCM → выход заняла около 2540 мс, поэтому среднее мало репрезентативно.

Дополнительно проверен полный Controller/DialogRuntime с управляемым
потоковым провайдером и настоящими SAPI/QAudioSink (громкость 0).
Провайдер отдавал первое предложение и ждал первого ActiveState,
только после этого отдавал второе. Подтверждено:

- Два последовательных запуска аудио без ошибок.
- Первый запуск выхода строго раньше окончания потока LLM.
- Первый PCM готов через 261.3 мс после запуска запроса.
- Первый ActiveState через 2880.4 мс от искусственного speech_end;
  холодное открытие выхода составило основную часть этой задержки.
- В истории две записи после завершения, все потоки закрыты.

Это контроль порядка выполнения с искусственным LLM, не результат
Ollama/Gemini и не измерение акустического звука. Пользовательские 7.7 с
в этом аудите не воспроизводились. Удалено последовательное ожидание
полного LLM и полного TTS; новая реальная задержка зависит от времени
первого предложения, выбранного TTS и холодного старта аудиоустройства.

TTS выполняется по готовым предложениям. Это не потоковое воспроизведение
отдельных MP3-пакетов внутри одного предложения; при медленном синтезе
следующего фрагмента между ними возможна пауза.
