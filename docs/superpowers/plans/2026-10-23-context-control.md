# Контекстные инструменты Alice Voice

Источник требований: приложенный пользователем текст от 23 октября 2026. Реализация в текущем каталоге, который не является Git-репозиторием. Существующие голос, память, Firefox и проверка владельца сохраняются.

Этапы:
1. Общий реестр: строгая схема аргументов, раздельные разрешения, структурированный результат, отмена, ограниченный журнал действий. Детерминированные знакомые команды остаются быстрым путём; модель разбирает остальные намерения в JSON, не исполняемый код. Контекст: последнее активное внешнее окно и история диалога. Модель не подтверждает опасные действия за пользователя.
2. Windows backend: каталог установленных приложений/ярлыков, окна, настройки, звук, яркость, скриншоты в RAM/буфер, медиа, папки. Неоднозначность возвращает варианты, launch сообщает только принятие команды, закрытие через WM_CLOSE сохраняет стандартные диалоги.
3. Питание: отдельный диалог состояний action → awaiting_yes → awaiting_exact → execution. Два разных входных utterance ID, 30 секунд на ожидание, явная финальная фраза. Стоп/нет/отмена сбрасывают. Никакого /f; запрос питания не является подтверждением.
4. Игры: наблюдение активного окна, OCR/доступные элементы/разрешённый визуальный анализ, одно действие и повторное наблюдение. Отмена и совпадение окна проверяются непосредственно перед вводом; устаревшие координаты не используются. Неопознанные элементы/защищённый ввод дают ручной следующий шаг. Автоматическая поддержка всех игр не заявляется.
5. GUI: отдельные переключатели возможностей, видимый статус подтверждений и управления вводом, последние действия, кнопка Стоп.
6. Проверки: RED/GREEN на схемы, естественные фразы, неоднозначность, два подтверждения, таймаут/отмену/неповторяемость, смену окна, единичные наблюдаемые действия. Полный существующий unittest, smoke GUI, неразрушающие native проверки; питание не выполняется на реальном компьютере в тестах. Если доступной игры нет или её меню не распознано, это явно фиксируется, не заменяется mock-результатом.

Разделение работы: Windows backend и UI можно реализовать независимо по фиксированным интерфейсам; основной агент ведёт реестр, модель, питание, сценарии и интеграцию. Перед завершением — независимое read-only ревью.
