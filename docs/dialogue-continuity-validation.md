# Диалог и ранняя озвучка — 23 октября 2026

## Причины и изменения

В settings.json история ограничена одной парой реплик. Код удалял старые пары
без резюме; предполагаемого сохранения первых символов ответа не обнаружено.
Добавлены точная недавняя история, ограниченное экстрактивное резюме вытесненных
фраз и отдельный TaskState. Исправления/решения пользователя получают приоритет;
слова модели об успехе остаются словами модели, а выполнение подтверждает только
результат инструмента. Дополнительных LLM-запросов на резюме нет.

Контекст принадлежит контроллеру, а не экземпляру модели, и сохраняется при
пересоздании служб. Незавершённая генерация не переносится. Состояние задачи
хранит цель, выбранное приложение/файл, завершённые шаги, ожидаемое уточнение,
последний результат и варианты выбора. Окно проверяется заново перед действием;
недоступное наблюдение не подменяется старым закэшированным окном.

Проверены браузер → поиск «там», список моделей Ollama → «выбери вторую»,
документ → «нет, другой» (запрос имени/пути, без произвольного выбора файла),
«объясни подробнее», смена темы и смена модели. Число внутри новой команды
громкости не выбирает вариант из старого списка. Прямого общего инструмента
открытия произвольного документа раньше не было; новый многошаговый исполнитель
файловых задач в эту доработку не добавлен.

Потоковые TTS/PCM-очереди и последовательное воспроизведение уже существовали.
Они сохранены. Убрана граница первой фразы на произвольном пробеле, добавлены
фильтрация thinking/JSON/блоков кода до TTS и проверка зависимых незавершённых
придаточных. Десятичные/группированные числа, сокращения и порядок фраз проверены.
Чанки аудио используются только через существующий stream_pcm выбранного адаптера;
Silero синтезирует последовательные фрагменты, это не нативная потоковая модель.

Silero.prepare перенесён параллельно с получением текста. Дополнительно обнаружена
и устранена общая очередь чтения памяти и синтеза: контекст больше не ждёт
освобождения единственного речевого исполнителя. Кэш убирает повторные SQLite-
чтения; приветствия и простые вычисления не получают ненужный блок памяти.
Пустые поля TaskState не раздувают запрос. Для установленной qwen3.5:4b
`/api/show` подтвердил thinking.values=[false,true], default=true; теперь
поддерживаемый think=false применяется и в ответах, и в разборе намерения.

Отмена сохраняет прежний механизм response token, дренирование очередей и
отбрасывание поздних PCM. Добавлены проверки после ожидаемого нативного действия,
защита поздних progress/action-событий и запрет записи отменённого ответа в историю.
Стоп не выгружает модели. AEC и расширенное голосовое перебивание не заявляются.

## Методика и ограничения измерений

Снимок исходников до изменений: `.build-tmp/dialogue-before/alice_voice`.
Стенд: `scripts/qa_dialogue_latency.py`. Три одинаковых запроса в процессе:
первый включает холодную подготовку Silero, затем два повторных. Состояние
серверного кэша Ollama не сбрасывалось; это не полностью холодный старт ОС/LLM.
Громкость QAudioSink была нулевой. Измерено время до готового PCM и события
запуска устройства; физически слышимый звук микрофоном не проверялся.

Вход этих парных прогонов — принятый текст. Микрофон, VAD/STT и ожидание конца
речи в эти числа не входят. Настройки endpoint 650 мс не менялись. Новые метрики
speech_end_to_first_text/speech_end_to_voice в обычном приложении используют
настоящую метку конца речи, но полноценная акустическая проверка конца речи →
слышимый ответ здесь не выполнена и не подменяется арифметическим прибавлением.

### Контролируемый replay, мс

Фиксированные задержки: LLM 50+50+80 мс, холодная подготовка TTS 300 мс,
синтез около 20 мс, медленное хранилище 40 мс. Это проверка накладных задержек
конвейера, не скорость настоящей модели.

| Этап | До | После |
|---|---:|---:|
| Первый текст, холодный | 407 | 88 |
| Первый PCM, холодный | 484 | 304 |
| Первый текст, прогретые повторы | 88; 91 | 45; 45 |
| Первый PCM, прогретые повторы | 150; 153 | 106; 108 |
| Чтения хранилища за три ответа | 3 | 1 |

Источник: dialogue-before-fixture-results.json / dialogue-after-fixture-results.json.

### Настоящие Ollama qwen3:1.7b + Silero + QAudioSink, мс

Одинаковый вопрос: «Сколько будет два плюс два?». Для обоих прогонов одинаково
ограничены max_tokens=96, max_response_chars=400; пользовательские настройки не
перезаписывались. Малый N и изменяющееся состояние CPU/модели не позволяют
объявить стабильный выигрыш на всех запросах.

| Этап | До | После |
|---|---:|---:|
| Первый текст, первый запрос процесса | 3715 | 2240 |
| Первый PCM, первый запрос процесса | 5979 | 4179 |
| Первый запуск аудиовыхода | 8056 | 6033 |
| Первый текст, прогретые повторы | 368; 70 | 279; 299 |
| Первый PCM, прогретые повторы | 2201; 332 | 2146; 459 |
| Запуск аудиовыхода, прогретые повторы | 2202; 332 | 2147; 459 |

Холодная задержка уменьшилась в этой паре, устойчивого ускорения прогретого
режима не доказано. Отдельно видны оставшиеся расходы первого синтеза Silero
около 1.7–1.9 с и первого запуска аудиовыхода около 1.9–2.1 с. Их не скрывает
среднее значение нескольких разных фаз прогрева.

Источник: dialogue-before-live-results.json / dialogue-after-live-results.json.

На одинаковом фиксированном тексте с настоящими Silero/QAudioSink паузы между
двумя фразами: до 0.026–0.038 мс, после промежуточной версии 0.023–0.059 мс.
Они уже практически нулевые. Это события устройства, не акустические замеры.
Полные исходные результаты: dialogue-*-native-phrases-results.json. Промежуточный
после-прогон сделан до окончательного отделения чтения контекста от TTS;
используется для проверки непрерывности, не доказательства ускорения.

## Проверки корректности

Итоговый проектный прогон после всех изменений диалога и памяти:
**430 тестов, 0 ошибок**, 50.146 с.

Тесты проверяют фразы до завершения HTTP, FIFO и backpressure, отсутствие
дубликатов/потери слов, отмену/поздние PCM, очистку очередей, сохранение контекста
при смене модели, уточнение неоднозначности, свежесть окна и статусы действий.
Отдельно воспроизведена и устранена блокировка запроса занятым исполнителем TTS.
В sandbox Windows asyncio зависал при создании socketpair; полный прогон выполнен
с необходимым доступом, вместо объявления этого зависания ошибкой приложения.

Следующий этап — многошаговые команды и акустически проверенное перебивание.
